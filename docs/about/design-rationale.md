# Design Rationale

> Understand why vitrify is built the way it is: its design positions, requirements and goals, the grounding of each schema region, its checks and thresholds, and the alternatives it rejected.

Use this page when you want the reasons behind a behavior — before proposing a change to vitrify, or when judging whether its trade-offs suit your project. It is the design reference: each position, requirement, check, and threshold, grounded in the sources it cites. For what the components are and how they connect, see [Architecture](architecture.md). You do not need this page to use vitrify.

> [!NOTE]
> Bracketed keys such as `[det-orch]` cite [Sources](../reference/sources.md). `[oracle]` is the behavioral oracle committed in this repository: the calc example and the golden corpus of the current schema version. Values marked **[j]** are judgment defaults: tunable knobs with no correctness weight. `RA-n` numbers a rejected alternative below.

## Design Positions

Four structural positions shape everything else:

- **All content lives in the binary; nothing is copied into harness discovery locations.** Copied living documents are a synchronization liability — harness-native extension surfaces demonstrably churn (the OpenHands delegation API this project's research fetched had been replaced upstream within months [openhands]) — so no per-harness artifact exists at all: every procedure is served on demand by `vitrify brief <task>`.
- **Deterministic orchestration, inference at the leaves.** A procedure a model follows varies run to run; the one controlled study on this axis finds deterministic orchestration achieves "comparable computational accuracy … while improving worst-case robustness and reducing performance variability across runs" [det-orch], and self-coordinated inter-agent orchestration measured worst in the one head-to-head on multi-agent coding (54.1% pass rate, "cannot substitute for … explicit cohesion-aware task partitioning") [cohesion]. So control flow, scheduling, and state transitions are Rust; the model is invoked at exactly three enumerated points.
- **No interpreter anywhere at runtime.** One static binary plus `git`; nothing else enters a repo, a harness sandbox, or a CI machine.
- **Agent-first presentation.** vitrify's caller is a coding agent working for a human. The installed binary carries everything the agent needs, where the agent looks — `--help`, the output of the command it ran, the error it hit — and in the version that is installed. Agents learn a CLI from its help, and no training data stands behind vitrify [cli-agent-lint] [arize]. `docs/` is for humans and for the reasons behind the design; no agent task needs it. [Agent-First Presentation](#agent-first-presentation) states the rules this position sets.

### Agent-First Presentation

These rules hold the fourth position in place.

- **Three places for documentation, no fourth.** The binary's documentation has the three tiers the large CLIs use, and new material goes into one of them:
  - task guides: `vitrify brief` lists the procedures and `vitrify brief <task>` prints one, as `git help -g` and `gcloud topic` serve guides [git-help] [gcloud-topic];
  - document formats: `vitrify schema show [--tdd]`, as `git help --developer-interfaces` lists file formats [git-help];
  - per-command help: each verb's `--help`, which carries its outputs, JSON fields and exit codes where `gh` keeps them [gh-help] (goal G7).

  Procedures are served one task each, in the binary's version; nothing versioned is copied into a project or a harness folder [poehnelt] [speakeasy] [clig]. RA-30, RA-31 and RA-32 reject a fourth place.
- **Guidance travels in the output.** Every lint and audit finding carries its remediation, and refusals, `vitrify new sdd`, `vitrify new tdd`, `vitrify pin sync`, `vitrify change apply` and the start of a run name the next command. Agents fetch what they expect to need and act on what is put in front of them; what they merely come across, they mostly ignore [explore-ignore] [clig] [writing-tools].
- **Repeated steps are one verb, and the gate is one verb.** When agents, or a project's scripts, chain the same vitrify commands every time, vitrify does it in one call — `vitrify change apply` for a change entry's bookkeeping — and `vitrify check` says in one call whether the repository is consistent. Agents skip detailed instructions, so every procedure ends in a mechanical gate [writing-tools] [skill-practices] [spec-growth].
- **Headless by construction.** Every verb but one is non-interactive, and none prints color, animation or pager, whatever its streams are connected to, which is what agent callers need [skill-scripts] [clig] [cli-agent-lint]. The one is `vitrify probe`, which asks before it changes `~/.vitrify/config.toml` — a file that is the user's from the moment `vitrify init` writes it — and changes nothing when no answer comes, as when an agent runs it with stdin closed; `-y` answers yes. Requirement R8 holds this, so a change cannot add another prompt; RA-33 rejects a second output for agents.
- **Project conventions stay the project's.** vitrify reads only spec files, file paths and exit codes (RA-17). A project's own conventions — a cross-SDD registry and its header rules, module maps checked against an import-boundary tool, shared Ground Rules text — are checked by the project's own scripts, which compose with `vitrify check`; `vitrify brief change` sends the agent to the project's own checks after `vitrify check`. RA-34 rejects an extension point for them.
- **Nothing lives outside the binary.** vitrify installs no agent material and writes no harness instruction file (requirement R9; RA-37, RA-38, RA-42). An agent learns of vitrify when its user names it, and everything after that comes from the installed binary.
- **Each release stands alone, and knows its version.** A release reads only its own formats and serves only its own commands, and the release notes say briefly what changed. What tells versions apart stays — `schema_version`, the refusal that names the version a release reads, the content manifest — so that change can be managed once vitrify reaches release status [clig] [cargo-metadata]. Agents relearn the interface from the installed binary in each session, so a breaking release leaves no stale copy behind [poehnelt]. The rule is [Versioning](../reference/formats.md#10-versioning); RA-39 and RA-40 reject the alternatives.
- **Docs say what is.** Help, error messages, briefs, schemas, templates, `docs/` and code comments describe the installed version only; history is in git, and the [Release Notes](release-notes.md) say briefly what each release changed. vitrify asks the same of the specs it governs — the spec text is always current truth, edited in place ([Changelog & change management](#schema-grounding)). Change records are folded into the documentation they amend and then dropped: "Specification changes, specification clarifications and documentation changes are removed from the specification update when the appropriate changes are made to the appropriate product specification or user documentation" [intel-spec-update]. Version control keeps the rest: "Source files are stored in version control to record editing history" [tf-vcs]. A project's notable changes are recorded in one place [ecs-changelog].

#### Help Is the Front Door

- **`vitrify --help` routes by task.** `-h` and `--help` print different things, as clap provides: "`long_*` variants are used when user calls the program with `--help` and "short" variants are used with `-h` flag" [clap-derive]. `vitrify -h` is the concise help clig describes — a description, the few command lines an agent runs first, and "An instruction to pass the `--help` flag for more information", with the most common commands at the start [clig]. `vitrify --help` adds the commands grouped by task, the conventions, and the exit-status table — exit codes belong in help "so the agent knows what each code means", as `gh` documents its own [skill-scripts] [gh-help] — on stdout, ending with the version and the project's home page [gnu-help].
- **Help is where agents look.** cli-agent-lint asks "Can my agent learn this CLI from --help alone?" [cli-agent-lint]. No training data stands behind vitrify as it does behind `gh`, where "the training data is doing most of the work" [arize], and agents "use the environment to fetch expected information" [explore-ignore]. In a vendor's test of three coding agents driving a CLI non-interactively, the agents went to `--help` first and drilled down: "agents don't need special documentation. They need better standard documentation in the places they already look." [memnexus-web]
- **Help routes; the briefs hold the procedures.** Algolia warns against assuming "that `--help` is sufficient context for an agent. It isn't." [algolia] So the root help's `Start here` lines name a procedure for each task — `vitrify brief authoring`, `vitrify brief change`, `vitrify brief run` — instead of holding the procedures themselves.

#### Every Command Documents Itself

- **Fixed headings.** Each verb's `--help` adds `Reads:`, `Writes:`, `Prints:` (the text form and each `--json` field), `Exit status:`, `Config:`, `Examples:` and `Procedure:` ([Help Text](../contribute/development.md#help-text)), and every argument has help. Brief tasks, `new` kinds and `--stamp` values carry per-value descriptions from `ValueEnum` doc comments [clap-web]. kubectl requires a `Long` text with "additional information about input, output, commonly used flags" and an `Example` block "covering the common cases", checked by a script [kubectl-conv]. Examples are "by far the most common referenced bit of documentation users will find" [12f-cli]; "LLMs rely on concrete I/O" [cobra-llm]; documentation combined with demonstrations "consistently achieves the best results" [play2prompt]. "The first line is the contract. The following lines are examples an agent can adapt." [arcjet]
- **Exact, because it is the only contract.** Commands, flags and output fields "become a contract once agents start using them" [arcjet] [infoq]. vitrify holds no interface across releases before 1.0.0, so the installed version's help is the only contract there is, and it must be exact. Tool documentation drifts — "functionalities of tools are frequently updated, deprecated, or extended" [draft] — so the conformance test ties every `vitrify …` line in the briefs and docs to the binary (G7), and insta snapshots hold every help text, so every wording change is reviewed [insta].

#### The Brief Index

- **One task per brief, listed by `vitrify brief`.** `vitrify brief` lists the procedures as `git help -g` lists git's concept guides [git-help]. Speakeasy bundled its docs into its CLI, "our doc site wrapped in progressive disclosure CLI commands", and learned that "A 50-line focused skill that solves one problem well is more likely to be read and applied correctly." [speakeasy] The pattern is to "make the CLI itself the documentation, queryable at runtime" [poehnelt], where "The context cost scales with the task, not with the API surface." [poehnelt-tax] Concise instructions guide models better than demonstrations alone [easytool], and documentation in the terminal "stays in sync with the specific installed version of the tool" [clig].
- **A brief says when it applies.** Every brief opens with its purpose, a `Use when:` line, a `Not for:` line and the vitrify version, and ends with the report it asks for. A guide that is "vague about when to activate" is used too often or not at all [speakeasy].
- **Other CLIs do the same.** Speakeasy's CLI labels its agent group "Docs & guided workflows for AI coding agents (start here: speakeasy agent context)" [speakeasy-web]; Entire's `agent-help` "generates its output from the installed Entire binary" [entire-web]; beads' `bd prime` prints its workflow context for agents [beads-web].

#### Guidance, Never a Guessed Command

- **Errors are documentation.** "If you can make errors into documentation, then this will save the user loads of time", and "suggesting to the user commands they can run next helps them learn how to use your program" [clig]. A great error message says "How to fix the error" [12f-cli]; tool builders "prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks" [writing-tools]. So every lint and audit finding carries a `remediation`, each refusal names the command that resolves it, and verbs that start a workflow name the next step; information placed in the agent's path gets used [explore-ignore].
- **Suggest, never run.** Arcjet attaches a `remediation` to each error and keeps fuzzy correction away from agents, who "should discover the interface through `--help`, completions, and skills, not through fuzzy runtime correction" [arcjet]; clig, writing for humans, says to suggest what the user meant [clig]. vitrify suggests and never runs a guessed command, which satisfies both: clap's "tip: a similar subcommand exists" stays, because it runs nothing.
- **Hints on stderr.** Hints are `next:` lines on stderr; stdout changes only by added JSON fields, so what an agent parses holds.

#### Change Procedures

- **`vitrify check` is the gate.** It runs lint, the audit, journal replay, the ledger check and the pin states over one SDD or all, in one call. Tools can "handle frequently chained, multi-step tasks in a single tool call" [writing-tools], and an agent reinventing the same logic each run is "a signal to write a tested script once" [skill-practices]. "If you give it something that comes back pass or fail, Claude can close that loop itself." [cc-best-practices] In spec-driven development, "deterministic checks gate merges" [sdad], and conformance is enforced by the drift gate [spec-growth]. OpenSpec's CLI reference recommends `openspec validate --all --json` for bulk validation by agents [openspec-web].
- **Every procedure ends in a verb that fails.** "I frequently saw the agent ultimately not follow all the instructions." [boeckeler] Conformance is "enforced by the drift gate rather than requested in prose" [spec-growth], so `vitrify brief change` ends in `vitrify check --all`, not in a reminder.
- **`vitrify change apply` executes vitrify's own rules.** The bump decides the bookkeeping: a PATCH entry re-records the moved traces (the editorial re-stamp), a MINOR or MAJOR entry marks the moved units Stale, and the marks declared equal the set the audit finds. Agents retry, so "'Create if not exists' is safer", and stateful operations want "a `--dry-run` flag" [skill-scripts]: an entry already recorded is skipped, and `vitrify change apply --dry-run` prints the same and writes nothing. OpenSpec closes a change mechanically too: "Each delta spec section (ADDED/MODIFIED/REMOVED) is applied to the corresponding main spec." [openspec]
- **A batch change is planned before it is made.** `vitrify brief change` has the agent write which SDD gets which entry, producers before consumers, and check it against `vitrify locate` and `vitrify pin list --all` before editing: "For batch or destructive operations, have the agent create an intermediate plan in a structured format, validate it against a source of truth, and only then execute." [skill-practices] A single vague requirement "propagates inconsistent edits across many files" [sdad]. Out-of-date specs "cause silent failures" [codified], so the text, the entry and the marks land in one commit. The brief tells the agent what a new hire would need to be told [writing-tools].

#### Authoring Starts From a PRD

- **Route first.** `vitrify brief authoring` starts from the human's Product Requirements Document (PRD) and runs `vitrify locate`: a PRD for a feature inside an existing SDD's scope becomes a TDD revision and a change entry (`vitrify brief change`); a PRD for a new scope becomes a new TDD and SDD. The process fits the change: a tool must offer "flexibility for a few different core workflows, for different sizes and types of changes" [boeckeler], and "Most changes should stay in Lite mode." [openspec]
- **Interview, then write.** The agent reads the PRD against the TDD schema and asks the human in rounds of at most five targeted questions until each TDD section can be written, writes each answer into the TDD, and records what is still unknown as an open question. "Interview me until you could write the spec, then write it to SPEC.md." [cc-best-practices] Spec Kit's clarify step "Asks up to five targeted questions about underspecified areas of the current spec and encodes your answers back into `spec.md`", and its template says "**Don't guess**" [spec-kit-docs].
- **Then the readiness checklist.** It is the gate Kiro runs before design, analyzing requirements "for logical inconsistencies, ambiguities, conflicting constraints, and gaps" [kiro] ([Authoring checklist](#schema-grounding)).

#### Operating a Run From an Agent Session

`vitrify brief run` operates a build from an agent session; these rules shape it.

- **Who starts it.** A build can take hours. Claude Code waits "2 minutes for a foreground command by default and can ask for up to 10 minutes" [cc-timeouts], and harnesses stop background commands when the task stops or the harness exits, including commands that detach [cc-changelog]. So a run is started by the human in their own terminal, or through the harness's background execution, which notifies on completion — Claude Code's background Bash, OpenCode's background shell calls [oc-tools], Codex's background terminals [codex-bg] — and never by a foreground call.
- **Wait without spending turns.** Every check re-sends the conversation: "every turn re-sends the whole history plus whatever the last tool call returned" [turn-cost], and Claude Code treats polling a background command's output file or sleeping while it runs as a defect [cc-changelog]. The harnesses' own waits run in five-minute windows: Codex's background poll window defaults to five minutes [codex-bg], and a Claude Code Monitor watch times out five minutes after it starts [cc-headless]. Where the harness cannot notify, the agent checks at most once per `run.status_check_seconds` ([Thresholds](#thresholds)). `vitrify run status --follow` is `gh run watch` — "Watch a run until it completes, showing its progress", with its `--exit-status` [gh-run-watch-web] — and run in the background, its exit becomes the notification.
- **The Never list.** The brief forbids writing a unit's code, claiming a unit, editing state, starting a second run, or reporting success before `Complete.`: a supervising agent "starts implementing tasks itself instead of waiting for teammates" and "can stop early too, deciding the team is finished before all tasks are actually complete" [agent-teams].
- **Hand back to the human.** An open `Q-###`, a unit set aside after repeated attempts, a command failing for a reason outside the spec, or workers making no progress go back to the human: "Hitting some consecutive-error-threshold might be a great place to escalate to a human" [12fa].
- **The run keeps its report.** Claude Code passes up to 30,000 characters of output inline; past that, the model gets a file path and "a preview of up to the first 2,000 characters" [cc-output-limits], and harnesses "truncate tool output beyond a threshold (e.g., 10-30K characters)" [skill-scripts]. The report is the last thing an hours-long run prints, so it is written to `.vitrify/logs/<job>/report.txt` and the run record, and `vitrify run status` prints it once the run ends — the `search_logs` that returns only the relevant lines, in place of a `read_logs` [writing-tools]. Agents "start tasks in the background and redirect output to files they can later inspect" [infoq], so what the run writes is readable after the fact.
- **The header names what to run next.** The run's header carries a `Watch:` line naming `vitrify run status --job <job> [--follow]` and `vitrify brief run`. The header begins the output, so it sits inside the 2,000-character preview [cc-output-limits]; clig asks for next-step suggestions [clig], and guidance in the agent's path gets used [explore-ignore].

Formal agent material — instruction files, skills, plugins, hooks, an MCP server, project files — is the obvious alternative to serving everything from the binary. Use this table to see where each harness looks for each kind, what the sources show, and the decision.

The sources also argue for shipping material beside the binary. Poehnelt: "**Ship a `CONTEXT.md` or skill files**: encode the invariants agents can't intuit from `--help`." [poehnelt] Arcjet's CLI "does not try to embed every piece of documentation into the binary" and points to a skill [arcjet]. Those CLIs need agents to use them unprompted. vitrify's use begins with its user naming it, and from there `vitrify --help` and the briefs carry everything.

Serving everything from the binary answers the three problems installed material brings:

- **User-wide installation is hard to test and lands in OS- and harness-specific places.** Nothing is installed user-wide; vitrify writes only under `~/.vitrify/`.
- **Project-level installation drifts, and every project must be refreshed on every release.** Nothing is written into a project (R9), so nothing drifts; everything versioned is served by the installed binary.
- **A per-project `init` step has no natural moment.** There is no such step, because there is nothing to install into a project: `vitrify init` sets the machine up once and writes only `~/.vitrify/`, and `vitrify brief onboard` is a procedure an agent follows.

## Requirements and Goals

These are the user contract and the measurable goals the implementation is held to.

**Requirements** (the user contract): R1 distinct separation of CLI tools from harness · R2 a dedicated orchestrator, not a harness agent mechanism · R3 orchestrator driven by inference · R4 two layers — a pure core library, the CLI binary on top · R5 CLI tools 100% Rust, no interpreter at runtime · R6 installed in the user's home and on PATH · R7 shared configs and sources under `$HOME/.vitrify` · R8 every verb non-interactive and terminal-independent — no prompt, color, animation or pager, whatever its streams are connected to — but for `vitrify probe`'s one question before it changes `~/.vitrify/config.toml`, which `-y` answers and a closed stdin declines · R9 in a repository, vitrify writes only what its verbs own — spec state, the templates `vitrify new sdd` and `vitrify new tdd` materialize, and `.vitrify/` — and never a harness's instruction files.

**Measurable goals**: **G1** all content lives in the binary, served on demand by `vitrify brief`/`schema`/`new`; nothing is copied into harness discovery locations. **G2** `vitrify run` invokes the model at exactly 3 enumerated points; control flow, scheduling, and state transitions are Rust. **G3** runtime dependency set exactly `{git}`; CI needs nothing beyond Rust and git. **G4** one binary in `~/.cargo/bin`, all shared state under `~/.vitrify`. **G5** the calc example builds to Complete with **zero spec-body edits**, and its trace hashes, journal replay, ledger projection, and audit findings on seeded-drift fixtures match the golden corpus of the current schema version. **G6** the calc example completes a full generation pass with 2 concurrent workers through ≥ 1 real harness CLI, terminating Complete with the evidence triple quoted. **G7** every subcommand's `--help` carries what it reads, writes and prints, its exit status, and examples; every `vitrify …` line in `crates/vitrify-core/assets/` and `docs/` parses against the binary — a tier-1 conformance test.

## Non-Goals

These are deliberately out of scope.

**Non-goals**: no interface held across releases before 1.0.0 — the [versioning rule](../reference/formats.md#10-versioning) governs instead: any release may change anything, and a change to the document format or the trace recipe raises `schema_version` and regenerates the golden corpus in the same reviewed change (RA-39, RA-40); no MCP server (RA-5) [tools-law]; no agent material installed by vitrify, in a repository or user-wide (RA-37, RA-38); no hosted service; no harnesses beyond Claude Code, Codex, OpenCode; no direct-API inference backend (RA-10) — workers ride the user's existing harness auth [cc-headless] [codex-exec] [oc-cli]; macOS + Linux only — Windows runs the Linux target in WSL 2, the harness vendors' own documented path [cc-setup] [cc-install-web]; not a general-purpose agent orchestrator — splitting/sizing is plan-time authoring work, never dispatch-time [cohesion] [nibzard].

## Schema Grounding

The SDD and TDD schemas are the documents an authoring agent reads; this section records why each of their rules is what it is.

`vitrify schema show` prints the SDD schema; `vitrify schema show --tdd` prints the TDD schema — the two normative documents an authoring agent reads, embedded and materialized like the briefs (`~/.vitrify/schemas/`). They are operative agent content: regions, laws, lifecycles, checklists, nothing else. The design grounding behind their rules is recorded here instead, so the documents the model loads stay lean.

The pair splits authority. The **TDD** records the why — problem, goals, architecture, rationale, rejected alternatives — and changes only by human-reviewed revision; the **SDD** records the what and exactly how — pins, layout, frozen contracts, units, gates, state — and changes continuously through change entries. That is the spec-vs-design-document split long-lived specs practice [tor-spec] [bip]; the TDD schema defines the handoff — the consumption map (which SDD region derives from which TDD section) and the SDD-readiness checklist. The SDD schema optimizes for five properties: living, concurrent, auditable, agnostic, decision-complete. Region by region, the grounding:

- **Shape & layout** — one SDD per scope, single file or bundle, one unit per file in bundle form so concurrent status writes never share a file: one scoped spec per subsystem for targeted retrieval [spec-growth] [codified] [boeckeler], change/spec folder layout [openspec], the requirements/design/tasks triad [kiro], plain text in version control [docs-as-code] [sdd-tools-web].
- **Metadata** — semver where MAJOR = contract or pin change; `Draft → Active → Deprecated` with no "Done": preamble headers and a defined status progression as long-lived-spec practice [bip] [openspec].
- **Overview & TDD reference** — cite the TDD, never copy it; local choices become `D-###` entries, genuine gaps become `Q-###` and never edit the TDD upward: rationale as a distinct, cited section [bip], ADR practice [adr-web], and the numbered TBD/TBR register driven to closure [incose] [tbd-web].
- **Ground rules** — uppercase-only normative keywords [rfc2119]; decision-completeness ("a sentence that leaves the implementer a choice is a defect") because ambiguity measurably forks implementations [ambiguity-cost] and generation demands specs "precise, complete, and unambiguous" [spec-kit-docs]; machine-consumable text with exact paths and names [codified]; the bounded reading-set law — every unit buildable from Ground Rules + pins + its own entry + its contracts alone.
- **Technology decisions** — every dimension pinned exactly, the lockfile owned by the foundation unit, a Commands block with deterministic exit codes [spec-kit-docs] [codified] [lockfiles] [pin-web].
- **Ownership** — exclusive and exhaustive path ownership with an `unmanaged` escape; unowned files are orphans, an audit violation [spec-growth]; directory-ownership practice [own-web]; overlapping files are where parallel work collides [worktrees]. Ownership is also the whole test-posture mechanism: a test is writable only by its owner.
- **Contracts** — every cross-unit surface frozen in exactly one contract before its consumers go Ready; consumption through contracts only, "never D's design or code" [spec-growth]; contract-driven development [spec-kit-docs]; design-first APIs and contract testing [contract-web]. A surface another SDD owns is consumed through a pin on its content hash — verifying traces again [mokhov], applied across SDDs ([External Contracts](../reference/formats.md#8-external-contracts)).
- **Work units** — EARS requirement forms [ears] [kiro] [ears-web] (or Given/When/Then [boeckeler]); verification planned as the requirement is written [hooks-req] [incose]; decision-complete Implementation blocks with exact paths and prohibitions [codified] [spec-kit-docs]; sized 2–8 requirements — one unit per session [huntley], with task descriptions detailed enough that parallel workers neither duplicate nor collide [langchain] [mar].
- **Execution order** — acyclic `depends_on`, a foundation phase that blocks everything, `[P]` groups of mutually independent units, walking-skeleton ordering [spec-kit-docs]; parallelism pays only for genuinely independent tasks [worktrees] [worktrees-web].
- **Verification gates** — exact command sequences, no judgment; a write-set check before every merge and an input check after it (the unit was built from the text mainline holds); the test posture is the author's per-unit choice — tests written before the build, during it, or none — with tests-first available per unit [spec-kit-docs]; the whole suite held to "once green, stays green" rather than to any posture; intent and evidence must agree to land [spec-growth] [vibe-survey] [hassan]; the fencing check at the integration gate — the resource validates the sequencer [chubby] and rejects tokens that went backwards [locking]; contract conformance in CI [contract-web].
- **Ledger, traces, journal** — the ledger is a derived projection; staleness is verifying-trace hash comparison [mokhov] over SHA-256 content addressing [nix] [progit] — the out-of-date check [make] as input-hash caches practice it [bazel] [cache-web]; the journal is event sourcing: append-only, replay reproduces the ledger [fowler] [kreps] [azure-es], NDJSON as the line format [ndjson-web], reconstructable history as the auditability bar [osmani-agents]; the seven-check drift audit compares desired state against actual state [spec-growth] [kiro] [drift-web].
- **Changelog & change management** — the spec is current truth, edited in place; history exists to compute impact [openspec] [sdd-tools-web]; spec and code move in the same change, never "code now, spec later" [spec-growth]; specs evolve with feedback rather than one-shot up-front [fowler-beck]; mechanical invalidation detection — the open research need the trace hashes answer [p2p]. vitrify holds its own documentation to the same rule: it states the installed version, and the release notes alone say what changed ([Agent-First Presentation](#agent-first-presentation)).
- **Concurrency protocol** — claim = lease [leases] with renewal heartbeats and advisory expiry [k8s-leases] [redlock], lapsed claims auto-reappear [sqs-vis] [zk]; correctness comes from the fencing token checked at the gate, not from clocks [locking] [chubby] [fence-web]; isolated working copies with disjoint write-sets, and semantic conflicts caught at the serial integration gate [worktrees] [worktrees-web]; unwritten cross-unit assumptions are the canonical multi-writer bug [cognition] [langchain] [mar].
- **Authoring checklist** — pass/fail lines before an SDD goes Active: checklists as "unit tests for the specification" [spec-kit-docs], pre-design gap analysis [kiro]; the plan-deep/build-cheap asymmetry is the architect/editor split [aider] weighed against the measured cost of ambiguity [ambiguity-cost]. The checklist runs after the PRD interview, which fills the TDD round by round and records what is unknown as an open question rather than a guess [cc-best-practices] [spec-kit-docs] ([Authoring Starts From a PRD](#authoring-starts-from-a-prd)).

## Audit and Lint

Each mechanical check exists to catch one kind of drift or authoring defect.

The **seven audit checks**: 1 orphans (files under `scope_roots` that git would commit — tracked, or untracked and not ignored — and that are neither owned nor `unmanaged`; outside a repository, every file on disk except under `.git` and `.vitrify`, tested on the root-relative path — the worktree-prefix rule); 2 ghosts (Built/Verified units whose globs match no file); 3 contract references (consumed contracts exist; contracts name existing units — spec only, since the audit never reads source code); 4 rotten Verified (re-runs Verification commands; `--skip-rotten` only where the gate just ran them); 5 trace mismatch; 6 projection consistency (replay vs front matter + the Stale-cause cross-check); 7 lapsed leases (`--fix-leases` formalizes the release). Finding shape `{check, subject, cause, remediation}`; exit 0 clean / 2 with findings.

The **eleven lint checks** (mechanizing the authoring checklist): L1 dependency graph acyclic; L2 ownership exclusive and exhaustive; L3 parallel groups independent; L4 contracts resolve both ways — a consumed contract exists, a contract names units that exist, and its `Consumers:` line is exactly the units that list it in `consumes`, its producer apart (the line restates what the units already say, and nothing else keeps a restatement true); L5 reading-set budget — every unit's readset totals ≤ `readset_budget_bytes`, because a unit must be buildable in one fresh session/context window [ctx-eng] [nibzard]; the unit's own entry is measured as authored, without the fields vitrify writes — the same masking the trace hash applies — so a unit sized against the budget cannot be pushed over it by being built; the budget is **byte-denominated by design** — workers span heterogeneous models whose tokenizers differ, encoding efficiency is literally measured in bytes-per-token and varies per tokenizer [superbpe], so bytes are the tokenizer-neutral unit, with ~4 chars/token as the sizing intuition [openai-tokens] (64 KiB ≈ 16K tokens); L6 requirement coverage (every `U-###.R#` in the Verification table); L7 pre-build state sanity; L8 no `OPEN(Q-###)` in Ready units, and no marker for a question the Decision Log does not hold; L9 every pin matches the body it stands for ([External Contracts](../reference/formats.md#8-external-contracts)); L10 `version` and `updated` are the last change entry's — the schema asks for a change entry per bump, and a bump without one is otherwise invisible; L11 the TDD pin — `tdd:` names a file, and an Active SDD pins the current revision of an Approved TDD, wherever the TDD's metadata is in the form vitrify can read (its own template's table; the TDD schema leaves the form to the author, so a TDD without it is held to the path alone). L1–L8 read one SDD; L9–L11 read what it names outside itself, which is where a single-SDD check has nothing to say. Lint is how a plan-time split is held to the partitioning evidence before `status: Active` — explicit dependency-aware partitioning is what beat self-coordinated runtime splitting [cohesion]. `--built` drops L7 for an SDD that has state — the subset preflight has always run — so the other ten keep holding after the build starts.

Use this table to see each default and its basis. How to change the values is in [Configuration](../cli/configuration.md).

|---|---|---|
| Worker cap default | 4 | the 2–4 band for bounded parallel work [oracle] [nibzard] |
| Lease / renewal | 60 min; renew < 25% remaining | queue-visibility-timeout sizing [oracle] [leases] |
| Worker hard budget | 120 min **[j]** | 2 × lease; bounds renewal of a hung worker |
| Escalation / giving up | 2 failed attempts of one unit → one escalation call; 4 → the unit is set aside for the run | the oracle's default of 2 [oracle], applied per unit |
| Gate jobs | one per CPU core **[j]** | the test-harness default — `cargo test` runs one test thread per available core, `--test-threads=1` the opt-out; here `gate_jobs = 1` |

| Agent's run status check | 270 s (`run.status_check_seconds`) | just inside a model provider's five-minute prompt-cache lifetime, with half a minute of margin because time spent generating counts against it [anthropic-cache-web] [openai-cache-web]: each check re-sends the whole conversation [turn-cost], and with cache reads at a tenth of the input price, 13 cached checks an hour cost about 1.3 full reads of the conversation against 3 for 3 uncached checks; raise it where a model's cache lasts longer |

## Rejected Alternatives

These doors are closed: each option below is rejected for the reason given, and reopens only through a reviewed design revision.

- **Model-run orchestration loop** (RA-1): deterministic orchestration matches LLM-controlled accuracy with better worst-case robustness [det-orch]; LLM orchestration is justified only when subtasks aren't pre-defined — an SDD pre-defines them [bea]; own the control flow in code [12fa].
- **Harness agent mechanism as the orchestrator** (RA-2): delegation APIs churn [openhands]; write-side multi-agent coordination fragments decisions [cognition]; self-coordinated teams measured worst [cohesion]. `brief kickoff` preserves manual operation without coupling correctness to any harness.
- **Dispatch-time task splitting by an LLM** (RA-3): splitting is model work at *plan time*, frozen and lint-validated; runtime partitioning produced conflicting interfaces and the lowest pass rate [cohesion]; sizing is the one-unit-one-session constraint [nibzard] [ctx-eng].
- **Symlinked or copied content distribution** (RA-4): copied living documents are a synchronization problem; content is served by the CLI at invocation time, never copied into harness locations [tools-law] [skills-spec].
- **MCP server surface** (RA-5): an MCP server's tool schemas cost context where a CLI costs nothing until it is invoked. Claude Code's tool search makes idle MCP tools cheap [cc-features], but on the other two harnesses "every connected MCP server injects its tool schemas into the context window on every turn" [tools-law] — "~72K tokens for 50+ MCP tools loaded upfront" [adv-tool-use] — and vitrify's verbs take flat flags, for which "the `--help` text defines the exact set of valid inputs" [ms-args]. Reopens if Codex and OpenCode load idle MCP tools as cheaply as Claude Code does and a verb's inputs outgrow flat flags.
- **libgit2/gix as the git layer** (RA-6): the correctness primitive *is* the git binary's own CAS and worktree semantics [update-ref] [rust-git]; precedent: Cargo's `net.git-fetch-with-cli` escape hatch [git-fetch-cli], jj's move off libgit2 toward shell-out [jj-shellout]. Re-opens only with measured spawn overhead.
- **Full YAML for front matter** (RA-7): masking operates on raw lines; YAML normalization breaks byte-identical hashing.
- **Per-verb binaries** (RA-8): one multi-call binary = one install, one version, one `--help` index [spec-kit-docs] [spec-kit] [rust-cli-book].
- **Async runtime** (RA-9): a few dozen long-lived subprocesses need `std::process`, one thread each and a channel, nothing more.
- **Direct-API worker backend** (RA-10): the first-party SDK exists [agent-sdk], but "Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK" [agent-sdk-web] — an API backend forces API-key billing on users who already pay for a harness; headless CLIs ride the existing login [cc-headless] [codex-exec] [oc-cli].
- **An interpreter anywhere at runtime** (RA-11): rejected by R5; the oracle is committed fixtures, so even CI needs none.
- **Crate name `vitrify`** (RA-12): unavailable — registered by an unrelated SPARQL tool 2026-10-08 [crates-vitrify]; published as `vitrify-cli`, binary name unaffected.
- **Plugin-channel distribution** (RA-13): a Claude Code plugin serves Claude Code alone and is installed per user — committing it to a project still leaves each collaborator to run `claude plugin install` [cc-plugins] — so it reaches one of the three harnesses, lands in a user-wide, harness-specific place, and cannot be tested from vitrify's own tests: the installation RA-38 rejects. Staleness is not the reason: a plugin is copied into a per-version cache [cc-plugin-cache] [cc-plugins-web], but one with a `command` source is rendered again once per session [cc-plugin-command]. Reopens under RA-38's conditions.
- **A declared test-posture field** (RA-14): the posture is already stated by ownership and Verification tables — the things the gates enforce — so a separate field could only drift from them.
- **Gate-observed tests-first** (RA-15): proving red-before-green means running a unit's checks before its work lands, but rows that rightly pass without the unit (lint, style, a dependency's tests) cannot be told apart without a per-row marker the author must keep true, and the post-merge green the gate already requires is the evidence that counts.
- **The §5 Test command as a preflight gate** (RA-16): its result before the build depends entirely on the test posture — no tests yet, tests awaiting their code, a runner that fails on an empty suite — so gating on it would force every SDD into one posture. Audit check 4, run at preflight, re-runs every Verified unit's Verification table: the posture-neutral baseline check. For the same reason the integration gate does not demand that Test pass — only that a merge not break it once it does: a build of fifteen bundles showed what the absence of any whole-suite check costs (a unit whose test module broke collection was stamped Verified, every row green), and an unconditional check would deadlock every bundle whose suite is red before its first test lands.
- **Worktrees under `.vitrify/`** (RA-18): the scratch directory carries a `*` ignore file, and an ignore-aware checker run in a worktree beneath it checks nothing and passes. Reproduced with tach 0.35.3 and one deliberate boundary violation: `tach check` exits 0 ("All modules validated!") in a git worktree under a directory whose `.gitignore` says `*` — though the worktree is a checkout of its own — and exits 1, naming the violation, in a worktree of the same commit at a path no ignore file covers. Only tach was tried. Dropping the ignore file would move the exposure to the repository's own ignore files and let tools run at the repository root walk every worktree. Outside the working tree neither can happen.
- **Deleting a taken branch or worktree name** (RA-19): removing whatever sits at a worktree path, and deleting any branch of the same name, before creating one is safe only if no one else can hold that name. Two SDDs in one repository each have a `U-001`, so with names carrying only the unit and the claim number, a run on the second would destroy what the first keeps at `U-001`, `c1` — work set aside from a blocked or rejected attempt included. Names carry the SDD, and a name that exists is someone's: refused, not replaced.
- **Waves** (RA-20): dispatching one parallel group, waiting for every worker, then integrating one unit at a time makes wall-clock time grow with the square of a bundle's size and leaves most slots idle. The dependency graph already says what may run together.
- **Cross-SDD scheduling** (RA-21): building several SDDs in one run would need an order between them, and nothing in an SDD states one. One run builds one SDD; a repository's SDDs are run in the order their authors know. What vitrify guarantees is that such runs cannot damage each other.
- **Sizing the model per unit** (RA-22): choosing a model from a unit's size or requirement count is a heuristic about a document vitrify otherwise never judges. The one signal it does have is mechanical — an attempt failed — and that is what selects the `retry` profile.
- **Hard-resetting the primary checkout** (RA-23): `git reset --hard` can be used only on a clean checkout — it overwrites an untracked file that sits where a published file goes — so a checkout with any local change at all would be left behind for the rest of the run, showing the run's commits as staged reversals that the next `git commit` would make real; and `git reset --keep`, the obvious remedy for that, leaves the files stale. A fast-forward of index and files carries local changes along and stops only at a real collision.
- **One Verification row at a time by default** (RA-24): every integration re-runs every Verified unit's rows, so a serial gate grows with the build — on a fifty-unit bundle, preflight alone took 79 s one row at a time and 25 s at eight. The protocol already asks that rows be hermetic, a row that fails beside others is confirmed alone before it counts, and `gate_jobs = 1` is there for an SDD whose rows share state: the model `cargo test` uses for its test threads.
- **Symlinking a consumer's contract to its authority** (RA-25): the authority's `Producer:` and `Consumers:` lines name the producer's units, and lint and the audit resolve them against the consumer's — where the same ids are other units. The consumer needs a header of its own, which is what a pin is: its own header, and the authority's body reached through the pin.
- **A neutral, contracts-only SDD** (RA-26): moving published contracts to a bundle no unit lives in adds pins instead of removing them. A producer reads its own contracts — every one of the 86 authorities in the fifteen-bundle build measured here is consumed by a unit of its own bundle — so each would need a pin there too.
- **Merging coupled SDDs** (RA-27): it removes the pins between them, and then every integration re-runs every Verified unit's Verification rows across all of the merged scope, and one Ground Rules edit stales every unit in it.
- **The pin check as a verb outside lint** (RA-29): `vitrify pin list` reports it, but a check only a verb runs is a check a run does not. The one failure it exists for — a build that uses the wrong text with nothing noticing — is prevented only if preflight refuses, and preflight runs lint.
- **Reading source code in the audit** (RA-17): catching cross-unit use outside contracts means understanding imports, which differ per language. A heuristic over file extensions, import keywords and path substrings works for Python-style imports and silently does nothing for many others (`#include`, `using`, `use crate::…`, relative paths, import blocks), so users cannot tell what they are protected by. vitrify reads only spec files, file paths and exit codes; an SDD that wants the boundary checked pins a checker for its language and runs it as a gate command. Built-in skip lists for Node or Python directories, in the orphan scan or in SDD discovery, fail the same way: git's ignore rules decide what is governed and where an SDD can be found.
- **A separate agent-help command or flag** (RA-30): an `agent` verb or a `--help-agent` flag. `vitrify brief` already is the documentation subcommand such tools build [speakeasy]. Agents given a separate agent-help command use it only to disambiguate, after `--help` [memnexus-web], and "Too many tools or overlapping tools can also distract agents from pursuing efficient strategies." [writing-tools] Reopens if, in everyday use, agents told to use vitrify read neither `vitrify --help` nor `vitrify brief`.
- **A machine-readable command catalog** (RA-31): a `describe` verb that emits every command's arguments as JSON [algolia]. vitrify's verbs take flat flags: "With args, the `--help` text defines the exact set of valid inputs", and in the same experiment JSON "never improved correctness and always increased cost" [ms-args]. The conformance test reads clap's command tree in-process and needs no catalog. Reopens if a verb takes structured input that flat flags cannot express.
- **`--explain <code>`** (RA-32): rustc's pattern, a longer explanation per error code [rustc-explain]. Every lint and audit finding carries its cause and remediation in the line itself, so there is nothing further to look up, and a second lookup is a step an agent can skip. Reopens if a finding's remediation cannot be said in its line.
- **Switching output when a harness is detected** (RA-33): Claude Code sets `CLAUDE_CODE_SESSION_ID` in its Bash subprocesses [cc-env], and a tool could key on it. One output contract serves humans and agents (R8); a second doubles what help documents and the tests hold, and harness signals change with the harnesses' own releases [openhands]. Reopens if an agent needs output a human does not, and the three harnesses set one documented signal alike.
- **An extension point in `vitrify check`** (RA-34): extra commands named in `.vitrify/config.toml` that `vitrify check` would run. A project composes `vitrify check` with its own script, and vitrify would be running checks over what it does not read (RA-17). An extension point no other project needs is a speculative capability [yagni]. Reopens when several projects run the same kind of check beside `vitrify check`.
- **A detach mode for `vitrify run`** (RA-35): a `--detach` flag that daemonizes the run. Harnesses own background processes. Claude Code stops "background commands that detach from their shell (for example under `timeout` or `setsid`)" when a task stops or Claude Code exits [cc-changelog], and OpenCode and Codex provide background execution with a notification or a poll [oc-tools] [codex-bg]. A run that daemonizes itself outlives the session meant to own it, holding claims and workers nobody watches. Starting a run is the job of the harness, in the background, or of the human; vitrify handles the signal a harness sends when it stops one [infoq]. Reopens if a supported harness offers no background execution.
- **A wait verb** (RA-36): `run wait --timeout`, which would block until the run ends or the timeout passes. `vitrify run status --follow` already blocks until the run ends and exits with its status, and a harness's background execution turns that exit into a notification. A second command for the same wait is an overlapping tool [writing-tools]. Reopens if an agent needs a wait that `vitrify run status --follow` under its harness's background execution cannot give.
- **An `init` verb writing agent files into a repository** (RA-37): it breaks R9 and brings in the per-project upgrade loop of the SDD tools that do it — "Run this inside each project to regenerate AI guidance" [openspec] — where a forced refresh can overwrite a project's customized files [spec-kit-docs] [speckit-upgrade-web]. Each project would need its files refreshed on every vitrify release, in each harness's own folders, and the step has no natural moment: `vitrify init` sets up the machine, not a repository, and `vitrify brief onboard` is a procedure an agent follows. Reopens only with RA-38, under its conditions.
- **User-wide agent material installed by vitrify** (RA-38): skills, hooks, and skill bodies filled at invocation through Claude Code's `` !`<command>` `` syntax running `vitrify brief` [cc-skills]. No single skill location is read by all three harnesses: Claude Code documents `.claude/skills` and `~/.claude/skills` [cc-skills], Codex `.agents/skills` and `$HOME/.agents/skills` [codex-skills], and OpenCode reads its own folders and both of those [oc-skills]. Each target is harness-specific, OS-specific and user-wide, and none can be tested from vitrify's own tests. A session-start hook adds a second copy of what an instruction file already loads [cc-memory], and a `!`-filled skill serves Claude Code alone. Skill files encode what agents cannot learn from `--help` for CLIs they must use unprompted [poehnelt] [arcjet]; agents consult skills only for tasks "beyond what they can handle alone" [skills-desc], and vitrify's use begins with its user naming it, from which point `vitrify --help` and the briefs carry everything. Reopens when both of these hold: (1) in everyday use, agents still miss `vitrify --help` and `vitrify brief` when the user names vitrify, so the user goes on pointing them at docs; (2) Claude Code, Codex and OpenCode read one skill location alike — Claude Code does not read `.agents/skills`, and the requests for it are open [cc-agents-skills-web]. Then a single version-free skill, `.agents/skills/vitrify/SKILL.md`, whose body only says to run `vitrify --help`, may be considered as a design revision.
- **Deprecation periods, aliases and conversion tools before release status** (RA-39): clig asks for "a lengthy and well-documented deprecation process" for any interface [clig], but that is a commitment a released tool makes. vitrify is at 0.y.z, where "Anything MAY change at any time" [semver-web], as experimental projects reserve for themselves [unreleased-api] [swift-he] [yash-versioning]. Agents relearn the interface from the installed binary in each session [poehnelt], and nothing versioned is installed anywhere else (RA-38), so a breaking release leaves no stale copy behind; an alias or a shim would only add a second interface for help and the tests to hold. What a deprecation policy will need is kept: `schema_version`, the refusal that names the version a release reads, and the content manifest [cargo-metadata]. Reopens at release status (1.0.0), where [Versioning](../reference/formats.md#10-versioning) takes the policy.
- **Reading earlier schema versions** (RA-40): every version read is a second meaning for a reading set, a trace and a contract to keep apart in the parser, the fixtures and the docs. A change to the document format or the trace recipe raises `schema_version` and regenerates the golden corpus in the same reviewed change; an SDD that declares another version is refused with exit 4, naming the version this vitrify reads, and `vitrify locate` still lists it. Declaring the version moves no trace — a trace does not cover the core front matter — so an SDD changes its declaration and keeps its stamps. Reopens at release status, with the deprecation policy; the `Schema` type can name more than one readable version.
- **A discovery test against real harnesses** (RA-41): a test that drives Claude Code, Codex and OpenCode through scripted tasks to measure whether they find vitrify's procedures. Nothing in the design waits on it: the cited evidence grounds the help and the briefs, and the conformance test keeps them present and accurate. Its cost is high and recurring: three harnesses installed and logged in, real model calls on every run, results that vary between runs, and a parser for each harness's event stream, whose formats change with the harnesses' own releases [openhands]. What it would measure shows in everyday use — users stop pointing agents at vitrify's docs — and RA-38's first condition rests on that instead. Reopens if everyday use cannot tell whether agents find vitrify's procedures.
- **A pointer in a repository's AGENTS.md** (RA-42): vitrify ships no lines for a repository's AGENTS.md or CLAUDE.md, and no step that writes them (R9). vitrify's use begins with the user naming it, and from there `vitrify --help` routes the agent. A pointer serves only sessions in which nobody mentions vitrify, and costs context in every session, since instruction files load in full on every request [cc-features]. An agent that never hears of vitrify and hand-edits spec state is caught by vitrify's own checks: lint, the audit, `vitrify check`, and `vitrify run`'s preflight. Nothing stops a user from adding such a line by hand. Reopens if agents edit spec state in sessions where nobody names vitrify, often enough that the checks catching it afterward costs more than the pointer.

## Technical Debt

The technical-debt register is empty — debt is the Cunningham/Fowler cruft metaphor [fowler-debt]; speculative capabilities are simply not built, per YAGNI's cost analysis [yagni]. Extensibility seams (the probed-argv table, the content registry) are in scope; speculative capabilities are not. Future scope arrives only as a new, reviewed design revision.
