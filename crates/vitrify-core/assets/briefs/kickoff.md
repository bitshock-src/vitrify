# Kickoff — the manual/interactive orchestration procedure

Drive an SDD from its current state to one of exactly two end states, from a
session, dispatching workers and one integrator yourself.

Use when: the build loop must run in a session — `vitrify run` cannot be
used here, or the human wants to drive it step by step.
Not for: unattended builds — `vitrify run` executes the same state machine
deterministically (`vitrify brief run`); building one unit
(`vitrify brief build-unit`); integrating one (`vitrify brief integrate`).
Version: vitrify {version} — every command below is this binary's.

The end states:

1. **Complete** — every non-Retired unit is `Verified` at the current SDD
   version; `vitrify audit` exits 0; `vitrify journal replay` exits 0;
   the SDD's §5 Test command, if it has one, exits 0 at the mainline head.
2. **Blocked** — remaining units are unclaimable, and each blocker is named:
   an open `Q-###`, a failing gate with its output, or a dependency chain
   rooted in one of those.

You plan and dispatch; you do not do the leaf work. Never write code, never
claim a unit yourself, never edit spec bodies, contracts, or the
ledger/journal/traces.

In a repository with several SDDs, every `vitrify` command takes `--sdd
<root>` — the SDD's root relative to the top of the checkout it runs in.
Working copies live under `{worktrees}`, outside the repository's working
tree, so that no ignore file of the repository hides their files from the
tools the gates run.

## 1. Preflight — refuse to start on any failure

1. SDD located and `Active` (`vitrify locate --units`), committed at the
   mainline head.
2. `vitrify check` exits 0 — lint (`--built` once units have state), the
   audit, the journal replay, the ledger and the pins. A pin that no longer
   matches its authority is a finding here: bring it in step through
   `vitrify brief change`, then start. Lapsed leases are fixed by
   `vitrify audit --fix-leases` (commit the fix through the claim publish
   discipline).
3. Every finding's fix is applied and committed; spec defects go through
   `vitrify brief change`, design questions to the human as `Q-###`.
4. The SDD §5 Commands bootstrap, build and lint run clean from the repo
   root. Test does not gate the start: whether tests exist or pass before the
   build is the SDD's test posture. From the first integration on it is a
   regression check — a merge must not turn it from passing to failing — and
   it must pass for the build to be Complete.
5. The machine is set up: `vitrify init`, or a later `vitrify probe`, has
   recorded at least one working harness in the machine's `config.toml`
   (absent CLI = "untested", never assumed). That is the human's machine
   setup, not a step of this procedure: if none is recorded, hand it back.
6. Shape rule: a single-file SDD caps workers at 1 — every status edit shares
   one file.

## 2. Job header (print before dispatching anything)

```
SDD build job — <slug> @ <version>
Done-condition: every non-Retired unit Verified @ <version>; audit clean; replay clean; §5 Test passing
Mainline: <branch>   Remote: <origin|none>   Shape: <bundle|single>
Plan: <phases/groups with unit IDs, from Execution Order + current ledger>
Workers: min(claimable units, cap)   Holder IDs: <job>-w<i>
Parameters: worker cap · lease minutes · renew fraction · escalate after N failed attempts of a unit
```

Correctness never depends on these values — lease expiry is advisory; the
fencing token is the mechanism. They tune throughput and reclaim latency.

## 3. Dispatch

One worker per claimable unit, cwd = that unit's worktree. Every dispatch
carries the full worker prompt generated by:

```
vitrify brief build-unit --unit U-### --holder <job>-w<i> --sdd <root>
```

Any claimable unit may be dispatched whenever a worker is free: two
claimable units are independent by construction — neither depends on the
other, each has its dependencies built, and ownership is exclusive — so
parallel groups are the author's plan, not a limit. Claim-then-build: each
worker slot claims first (`vitrify claim`); a lost race (exit 5) just means
that slot takes the next claimable unit. Never spawn idle workers. One
integrator, always exactly one, runs the `vitrify brief integrate` procedure
serially, as units report.

A unit whose last attempt did not land has that attempt's work on its branch
(`sdd/<sdd>/<unit>/c<seq>`): the prompt `brief build-unit` generates says
so. Never delete a branch or worktree you did not create.

## 4. Orchestration loop

```
derive state (vitrify locate --units + vitrify ledger progress + vitrify audit)
                                  # never trust memory — resume = re-derive
while claimable units exist or work is in flight:
    spawn  = a worker for each claimable unit while one is free (Stale units
            rejoin), claim-then-build — do not wait for the others to finish
    collect each worker's one-line JSON report as it arrives
    integrate every "built" branch — SERIALLY, one gate at a time
    "blocked" reports: land the Q-### Decision-Log entry (marked open) as a
            mainline commit if the worker could not; continue with units it
            does not affect; the unit rejoins when its reading set changes
    rejected or released: keep the attempt's work on its branch; the unit
            returns to the pool
    after integrations: audit; re-derive; lapsed leases → pool; units whose
            recorded trace no longer matches → Stale (`vitrify audit
            --apply-stale`, committed); prune merged worktrees and branches
    a unit that fails twice running → escalate before a third attempt
```

## 5. Model-strength guidance

Strongest model for orchestration and integration judgment; economical
models are fine for implementers — units are bounded, decision-complete work.
Escalate persistent integration failures to the strongest available model
before giving up.

## 6. Termination and report

* **Complete**: quote the final `vitrify ledger progress` line, `vitrify
  audit` exit 0, `vitrify journal replay` exit 0, and the §5 Test
  command's exit 0.
* **Blocked**: the final progress line, plus per remaining unit: the open
  `Q-###` (`vitrify questions --open` lists them with the units they
  block), the failing gate command and its last output lines, or the
  dependency chain rooting in one of those. Never report success on a red
  audit.

The report ends with the journal tail (last few events).
